# ローカル取り込みのプロトタイプ

クラウドの routine と同じことを PC 上で完結して行う実験。まだ本番運用には入れていない。

## なぜこの形か

routine の工程を分解すると、判断が要るのは一部だけだった。

| 工程 | 手段 |
|---|---|
| 受信箱を読む / アーカイブ | `gmail_client.py` — LLM 不要 |
| Google マップ URL から店・住所・座標を取る | `maps_resolver.py`（Playwright） |
| **マップ URL が無いメールを件名で検索して補完** | `maps_resolver.Session.search()` |
| 公式サイトの本文を読む | `maps_resolver.Session.text()` |
| タグとオススメメニューを決める | `tagger.py` — **ここだけ LLM** |
| restaurants.md に追記 | `restaurants_md.py` — LLM 不要 |
| build / commit / push | `run.py` — LLM 不要 |

要点が4つある。

**1. Gmail はローカルで認証できる。** claude.ai の Gmail コネクタが使えないのは、OAuth の
redirect URL が claude.ai 固定だから。自分で「デスクトップアプリ」型の OAuth クライアントを
発行すれば redirect は `http://localhost` になり、普通に通る。初回だけブラウザで認可して、
あとは refresh token で無人実行できる。

scope は `gmail.modify` だけ。読み取りとラベルの付け外しは許すが、完全削除と送信は
許さない。「削除・送信をしない」という制約をトークンの権限で担保している。

**2. Playwright が README の詰まりを解く。** 本体の README 設計メモにある「Google マップの
共有 URL は JavaScript 描画のため住所を取れない」は、ヘッドレスブラウザなら解決する。
しかも place ページの URL には実際の座標が `!3d<lat>!4d<lng>` の形で入っているので、
**国土地理院のジオコーダに頼らず座標が手に入る。**

**3. Web 検索も同じ経路に乗せる。** マップの共有 URL が無いメール（SNS のリンクだけ、
紙面の店名を打っただけ）は、件名から `https://www.google.com/maps/search/<店名>` を
組み立てて同じ `place()` に流す。検索エンジンを別途スクレイピングするより、検証済みの
経路を使い回すほうが壊れにくい。

1軒に絞れたかは **URL ではなく詳細パネルが開いたか**で見る。実物で確かめたところ、
1軒に決まっても URL は `/search/` のまま留まることがあった。住所（`data-item-id="address"`）は
詳細パネルの要素で、候補が並ぶ一覧には無いので、名前と住所が揃っていれば1軒に決まっている。

絞れなかったときと、出てきた店名が件名と一致しないときは、**選ばずに受信箱へ残す。**

同一性は**正規化後の包含関係**で見る。類似度で測ってはいけない。このリストには鳥貴族8店・
サイゼリヤ8店・福よし5店があり、支店名以外は同じ文字列になる。文字バイグラムの重なりで
実名58件を総当たりすると、**1653ペア中72組が誤一致**した（最悪は「サイゼリヤ イオンモール
旭川駅前店」と「同 旭川西店」の 0.86）。閾値を上げても解けない。包含なら誤一致は0。

**4. LLM に知識を思い出させず、規則はコードで確かめる。** 住所を「調べさせる」と小型
モデルは平然と捏造する。`tagger.py` に渡すのは、マップと公式サイトから取ってきたテキスト
だけ。そこからの分類に閉じているので、ローカルの 8B クラスでも成立する。`ClaudeTagger` と
`OllamaTagger` は入出力が同じで差し替えられる。

タグ規則（既存を使い回す・新タグは1つまで・「〜屋」のような語尾を付けない）は、プロンプトで
頼むだけでは守られる保証が無いので `enforce_tag_policy()` で検算する。守られないと地図の
絞り込みボタンが表記ゆれで二重に増え、**AND 検索なので「ラーメン」と「ラーメン屋」の両方を
選ぶと0件になる。**

## セットアップ

### 1. Gmail の OAuth クライアント

1. [Google Cloud Console](https://console.cloud.google.com/) でプロジェクトを作る
2. 「API とサービス」→ Gmail API を有効にする
3. 「OAuth 同意画面」を作る。ユーザーの種類は**外部**、テストユーザーに
   `restaurant.map23@gmail.com` を追加する（公開申請は不要）
4. 「認証情報」→ OAuth クライアント ID → 種類は**デスクトップ アプリ**
5. JSON をダウンロードして `~/.restaurant_list/credentials.json` に置く

### 2. 依存

```bash
pip install -r requirements.txt
playwright install chromium
```

`ClaudeTagger` を使うなら `ANTHROPIC_API_KEY` を設定する。`OllamaTagger` なら
`ollama serve` が動いていればよい。

### 3. 動かす

```bash
python run.py                      # dry-run。何も書かない
python run.py --apply              # restaurants.md に書いて build まで
python run.py --apply --push       # push してアーカイブまで
python run.py --tagger ollama      # ローカル LLM を使う
```

初回の `python run.py` でブラウザが開いて認可を求める。以降は開かない。

部品を単体で試すこともできる。

```bash
python maps_resolver.py "https://maps.app.goo.gl/..."
```

### 4. 定期実行

Claude Code に OS レベルのスケジューラは無いので、cron / launchd / タスクスケジューラから
叩く。

```cron
23 7 * * * cd /path/to/restaurant_list/prototype && /usr/bin/python3 run.py --apply --push >> ~/restaurant_list.log 2>&1
```

Windows はタスク スケジューラ。「操作」に以下を入れる。

```
プログラム: pythonw.exe
引数:       run.py --apply --push
開始場所:   C:\lab\git\restaurant_list\prototype
```

PC が 7:23 に起きている必要がある。ノート PC だと取りこぼす。

## 安全側の設計

- **dry-run が既定。** `--apply` と `--push` は明示的に付ける
- **アーカイブは push が成功したときだけ。** 途中で失敗したらメールは受信箱に残り、次回また拾われる
- **`--push` は main でしか使えない。** `git commit` は現在のブランチに乗るのに
  `git push origin main` はローカルの `main` を押すので、別ブランチにいると push が
  素通り（返り値0）になり、成功と誤認してアーカイブしてしまう。先に止める
- **住所が取れなければ行を足さず、アーカイブもしない。** 地図に置けない行は足す意味が薄い。
  なにより、Google の DOM が変わってセレクタが腐ったとき、`未確認` だらけの行が静かに増えて
  元メールは消えている、という壊れ方が一番まずい。住所が無ければ何も書かずに残せば、
  取り込めないメールが受信箱に溜まって気づける。直して再実行すれば全部拾い直せる
- **追記は行の挿入だけ。** 既存行は読みも書きもしない。来店回数と評価は利用者の記録なので、
  そもそも触りようがない構造にしてある
- **裏が取れなければ `未確認`。** 推測で埋めない
- **その年だけの情報は書かない。** マップの営業時間には「月曜日(敬老の日)」のような
  祝日名が混ざる。恒久的な一覧に書くと翌年から嘘になるので落とす。
  ただし「祝休日の営業時間」は*その時刻が通常の週間営業時間ではない*という意味なので、
  消すと嘘の記録になる。`（祝日）` の印にして人が見直せるようにする
- **特定できないメールは触らない。**「受信箱に残っている＝未処理」を保つ

## 検証状況

どちらもネットワークに出ない。合わせて 137 項目。

```bash
python test_extraction.py     # 部品の抽出ロジック（81）
python test_pipeline.py       # run.py の判断ロジック（56）
```

### `test_extraction.py` — 部品

- Gmail の MIME 解析（multipart、text/plain 優先、HTML のみのメール、script 除去、href 抽出）
- OAuth の権限が `gmail.modify` に限られていること（広がると削除・送信が可能になる）
- トークンの自動更新（無人実行の経路。ブラウザを開かず、更新後を 600 で保存）
- 店名の同一性判定。**実名58件・1653ペアの総当たりで誤一致ゼロ**を固定してある
- タグ規則の強制（語尾ゆれを既存に寄せる、新タグは1つまで）
- LLM が壊れた JSON を返しても落ちず、確信なしとして受信箱に残す
- 座標パース（`!3d!4d` を `@` より優先、短縮 URL は座標なし）
- 住所の書式合わせ（郵便番号・都道府県を落とし、数字を半角に）
- restaurants.md の追記（行数 +1、既存行は1行も不変、`|` のエスケープ往復、来店回数 0 / 評価 -）
- Google マップ DOM からの抽出（店名・住所・公式サイト・電話）
- 営業時間（畳まれた状態からの展開、aria-label からの回収、1日分なら書かない、
  実物から取れた生の値の整形 — 祝日の注記を落とし月曜から並べる）
- 情報が無いページで `None` を返す（＝`未確認`。捏造しない）

### `test_pipeline.py` — 何を書かないか

Gmail・マップ・タガー・git を差し替え、`build.mjs` だけ本物を temp 上で走らせる。

| 状況 | 期待する振る舞い |
|---|---|
| 受信箱が空 | 何も書かず exit 0 |
| dry-run | 書かない・アーカイブしない |
| 店を特定できない | 行を足さず**受信箱に残す** |
| マップ URL が無い | 件名で検索して補完し、住所まで埋める |
| 検索で1軒に絞れない | 推測で選ばず**受信箱に残す** |
| **住所が取れない** | **行を足さず、アーカイブもしない** |
| 公式サイトがある | 本文を読んでタガーの材料に加える |
| 材料が足りない | 行を足さず**受信箱に残す** |
| タグ規則に反する | 行を足さず**受信箱に残す** |
| タグが表記ゆれ | 既存の表記に寄せて追記 |
| 既に載っている | 行を足さず、メールだけアーカイブ |
| **main 以外で --push** | **commit も push もせず中止**（静かに失う経路）|
| **push に失敗** | **1件もアーカイブしない**・非ゼロ終了 |
| 成功 | 1行追記、新規も既出もアーカイブ |
| いずれの場合も | 既存行の来店回数・評価が不変 |

座標については、`build.mjs` がジオコーダに到達できない状況（＝クラウド routine と同じ）で、
Playwright が取った座標が `docs/data.json` に入り、既存店の座標も保たれることを確認済み。

DOM の検証は固定 HTML に対するもの。**セレクタの書き方とブラウザの配線が正しいことまでは
言えるが、Google の実物の DOM が fixture どおりかは別問題。**

## 未検証・弱いところ

- **実物での確認は1店だけ。** 2026-09-19 に津別町の1軒で店名・住所・座標・電話が
  取れることを確認した。営業時間も展開処理を足して7曜日ぶん取れることを確認済み。Google の DOM は予告なく変わるが、腐れば住所が取れず
  受信箱に溜まるので、気づける壊れ方にはなっている
- **Google のボット検出**に当たる可能性がある。`--headful` で回避できることが多い。
  検索を挟むぶんアクセスが増えるので、ここは実運用で様子を見る必要がある
- **営業時間は取れたり取れなかったりする。** 情報パネルより遅れて描画されるためで、
  同じ URL で成否が分かれた。待ちを入れたが、確実ではない。取れなくても
  メモが薄くなるだけで取り込みは動く（住所が取れていれば行は追加される）
- **件名が曖昧なメール**（「すすきのの店」など）は検索で絞れず受信箱に残る。
  いまの routine は「賢さ」で吸収しているが、こちらは残して人に委ねる
- **`tagger.py` の `confident` 判定は未チューニング。** 実 LLM を呼べていないため
  （この環境に API キーが無い）。外れても受信箱に残るだけなので害は小さい
- **`ClaudeTagger` / `OllamaTagger` の実呼び出しは未検証。** 呼び出し前後の契約
  （プロンプト・スキーマ・戻り値の扱い・タグ規則）は検証済み
- **OAuth の初回認可フローは未検証。** 実際の credentials.json が無いため
